Chrome's `moderate` document rule is a viewport heuristic, so it would add background requests the owner forbade. both reasons are carried from design (b) and are verified by code read plus the spec.

measurement does not favour Astro `ClientRouter`: it adds about 5.3 KB gz per document and still swaps and re-hydrates both AdminLayout roots (phase 1, likely). switching inside the island stays preferred.

**`claims()` is an allowlist, never a prefix or a segment count.** an earlier draft left the predicate unstated, which would have been a live hazard: `/content` holds six AdminLayout routes that the editorial island cannot render (`pages/content/edit/[pageKey].astro`, `content/review.astro`, `content/drafts.astro`, `content/carousels.astro`, `content/operations.astro`, `content/preview.astro`; verified, source: only `newsletter.astro`, `content/index.astro`, `content/dev-catalog.astro`, `content/[collection]/[id].astro`, `content/new.astro` and `newsletter/[slug].astro` use `EditorialLayout`). a `/content/*` prefix or a two-segment `/content/<collection>/<id>` match claims `/content/edit/home` and `/content/drafts`, `preventDefault` runs, and the island commits a route it has no data or component for. the throw fallback at 2.3 step 9 does not catch that, because a wrong-but-successful commit never throws.

`AdminLink` receives what Astryx passes: `href`, `to` (added by `createLinkWithTo`, verified, source `Link/useLinkComponent.ts:35-55`), `onClick`, `ref`, class and ARIA props. it strips `to` and renders a plain anchor. `LinkProvider` is `LinkContext` with `{component}` (`Link/LinkProvider.tsx:55-58`), resolved as `as ?? ctx?.component ?? two Astryx facts the click path must respect (verified, source, from the router spike): `Button` calls the consumer's `onClick` inside its own handler and passes that handler to the link component (`Button/Button.tsx:625-642`), and a `Button` with `isLoading` renders a `<button>`, not the link component (`:600-609`), so a link that becomes pending mid-leave stops being an anchor. the router must never depend on the pending link staying a link.

### 2.3 click algorithm (AdminLink)

1. call `props.onClick` first, so Astryx closes the drawer and applies its disabled guard. return if `defaultPrevented`.
2. return without `preventDefault` on non-primary button, any modifier, `download`, a `target` other than `_self`, or a cross-origin URL. the browser does exactly what it does today.
3. same path and search as the current location: `preventDefault` and stop (matching `HomeEditor.tsx:317-321`).
4. **run every registered guard whose `holds(to)` is true, before the denylist bail.** this is the fix for the sign-out hole: `/auth/logout` is denylisted for resolution, not for the guard, so a dirty draft leaving through Log out is flushed before the document navigation (verified hazard: the no-guard control lost the edit 5 of 5, router spike s1).
5. find the first resolver whose `claims(to, from)` is true. no resolver and no guard: return, native navigation runs.
6. `preventDefault`. `await guard.leave(to)`; false stops here and the editor shows its held-leave copy (`HomeEditor.tsx:264-276`).
7. with a resolver: `replaceState` the current `scrollTop`, `pushState` a new `AdminHistoryState`, call `resolver.commit` inside the click handler so React renders at discrete priority, apply title, scroll and focus after the commit, emit the compatibility events once.
8. guard allowed but no resolver: `location.assign(to)`. the editor is saved, so `beforeunload` (`HomeEditor.tsx:709-721`) stays quiet.
9. a resolver that throws: log, fall back to `location.assign(to)`. the router never leaves a blank route.

commits never use `startTransition`: a transition keeps the old screen up and pushes first change past the click. the record open never uses `React.Suspense`, for the reason in 2.4.

### 2.4 the editor module choice is frozen per open

`RecordRoute` holds explicit wait state. when the route commits it reads `loadHomeEditor.resolved()` once and stores the answer in route state:

| stored value at open    | render                                                                                                                                                                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| module already resolved | render the module directly. measured 112 ms click to editor-usable and 1 announcement                                                                                                                                                                                                  | verified, spike s3 |
| module not resolved     | render `EditorPlaceholder`, await the import, then `setState` the module. a `React.lazy` path would cost 380 ms and 2 announcements, because React 19.2.8 holds a revealed boundary 300 ms after the fallback commits (`react-dom/cjs/react-dom-client.production.js:10793`, `:11858`) | verified, spike s3 |

the stored choice never changes for the life of the open. the spike warns that a later re-render swapping the subtree remounts the editor and drops its state, so `RecordRoute` must not compute the branch during render. the cold-chunk production case is unmeasured (unproven, R17), so the one-announcement claim on a cold open is a design property, not yet evidence.

**the import is bounded.** `import()` takes no `AbortSignal` and a stalled chunk request (captive portal, proxy, flaky link) neither resolves nor rejects, so an unbounded await leaves `EditorPlaceholder` on screen forever. section 5's `code_unavailable` only covers a **rejection**, a chunk removed by a deploy, and the 15 s bound section 5 does specify belongs to the record read (matching the existing `AbortSignal.timeout(15000)` at `HomeEditor.tsx:456`, `:464`, `:493`, verified, source). so `loadHomeEditor()` races the import against a 15 s rejection, clears its memo on that rejection so a Retry re-imports, and the timeout maps onto `code_unavailable` with a document Reload. R8's experiment gains a case: build A, serve, open `/content`, **stall** the chunk response rather than deleting it, assert the placeholder resolves into the banner inside the bound.

### 2.5 leave guard

**two guards, not one.** an earlier draft registered only HomeEditor's, which silently removed `/content/new`'s protection the moment row 4 became an in-island route: `NewWriting.tsx:117-125` registers a `beforeunload` guard when `recoveryFailed` is true and a title or slug exists, which is exactly the case where the typed values live only in React state because the recovery write failed (`recoveryFailed` set from `channel.write` at `:109-115` and `:151-153`, all verified, source). today the side-nav click out of `/content/new` is a document navigation and that guard fires. an in-island commit never fires `beforeunload`, so without a registered guard the title and slug vanish with no prompt, and the unmount races the pending `channel.write` at `:145` and the tombstone at `:188`, which is the same hazard 2.5 step 2 fixes for HomeEditor.

| guard                 | `holds(to)`                                | `isDirty()`                                                                               | `leave()`                                                                                                                                                           |
| --------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HomeEditor            | false for the same record path             | the `beforeunload` checks (`HomeEditor.tsx:710-717`)                                      | below                                                                                                                                                               |
| NewWriting (new, S15) | true for any URL other than `/content/new` | `recoveryFailed` and a non-empty title or slug, or a create in flight (`pending.current`) | await the outstanding `channel.write` and any in-flight create, then return true; a create in flight returns false and holds the leave with the existing error copy |

HomeEditor's guard: `holds(to)` is false when `to` is the same record path, so views and panels stay free. `isDirty()` reuses the `beforeunload` checks (`HomeEditor.tsx:710-717`). `leave(to)`:

1. flush the three buffers and `await editor.flush()` (today's `leaveDocument` body without its last line, `:262-276`).
2. **`await` any outstanding browser-recovery write.** `close()` sets `this.closed` (`browser-recovery.ts:141-142`) and `write()` checks it both before and inside the `navigator.locks` round trip (`:169`, `:178`, lock at `:254-260`), while HomeEditor's load effect cleanup calls `recoveryChannel.current?.close()` on unmount (`:611-615`). an in-island unmount wins that race, so the queued `write(null)` tombstone is dropped and the next open offers to recover edits that were already saved: 5 of 5 without the settle, 0 of 5 with it, about 12 ms (verified, spike s1b; all four source citations verified, source).
3. return true only if the state is `saved`, no buffer is dirty and no edit arrived during the flush. a refused save sets `leaveRefused` and returns false.

this guard is required, not optional. a provider link calls `preventDefault` at the React root before HomeEditor's document listener runs, so that listener skips its flush (proven, 15 of 15). the spike's control with guards disabled unmounted the editor at 20 ms, sent nothing, and the edit survived neither the server nor browser recovery, 5 of 5 (verified).

one existing defect ships on this path and is fixed in the same PR: a 503 leave shows two `role=alert` banners for one failure (the held-leave copy plus "Draft could not be saved"), with two 503 attempts per run because the 600 ms autosave timer fires again (verified, spike s4). that contradicts the one-announcement rule.

### 2.6 popstate

one listener, registered at module evaluation so it runs ahead of every component listener. without that, HomeEditor's own handler (`HomeEditor.tsx:410-418`) calls `navigateWorkspace`, bumps `navigationGeneration` and makes the pending flush look stale (verified, spike api lesson).

1. a pending `skipGuardOnce` flag lets the completing traversal through.
2. a guard holds the popped URL and `isDirty()`: hold the traversal, `await guard.leave(popped)`, then complete it. how the hold is implemented depends on the browser, see below.
3. a resolver claims the popped URL: commit with cause `popstate`, restore `scrollTop` in the next animation frame. React assigns discrete priority to `popstate` (likely, R5).
4. no resolver claims it: `location.replace(location.href)`.

**the hold, corrected.** an earlier draft shipped the `pushState` restore everywhere and claimed "`history.length` unchanged at 3" as verified. that number is real but it is the single-entry case only, and the general claim is false. record subpages push their own entries (`HomeEditor.tsx:352-394`, `pushState` at `:379`), so the forward stack is routinely deeper: `/content` (1), open record (2), Preview (3), Back to (2), which the guard does not hold because `holds(to)` is false for the same record path, edit until dirty, Back to (1). `popstate` fires with the browser already at index 0, so a `pushState` truncates entries 2 and 3 and appends one. `history.length` goes 3 to 2 and the Preview entry is gone. R14 already conceded this; 2.6 and S15 contradicted it. the flat claim is removed from both.

so:

| browser                                                                    | hold                                                                                                                                                                                                                                                          | cost                                                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Navigation API present with a cancelable `navigate` event (Chromium)       | `preventDefault` the traversal, `await leave`, then `navigation.traverseTo` the popped entry. kept the record URL with 0 popstates 5 of 5 (verified, spike 2b)                                                                                                | none: the stack is untouched                                                               |
| Safari, Firefox, and Chromium where the `navigate` event is not cancelable | `pushState` the held record URL back (measured 3.3 ms after the popstate, 5 of 5), `await leave`, set `skipGuardOnce`, `history.back()`. save `responseEnd` 28.5 ms after the popstate, traversal after the save 5 of 5, unmount 61.3 ms (verified, spike s2) | **known cost: forward history beyond the held entry is truncated.** documented, not hidden |

Chromium's activation rules for repeated traversal cancels are unproven (R14), so the fallback stays shipped and tested, and a feature test picks the path at module evaluation. S15 must exercise both paths with **real input** on a forward stack deeper than one entry, not CDP.

### 2.8 prefetch

intent only. `AdminLink` composes `onPointerEnter`, `onFocus`, `onPointerDown`, `onPointerCancel` and `onKeyDown` with any Astryx handlers, then calls `router.intent` with `event.pointerType`. no viewport observer, no idle callback, no timer that starts work.

| destination                                                  | hover or focus                | press                                                                                                                                                                                          | cost                                                                                                                                                                                  |
| ------------------------------------------------------------ | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content groups, Newsletter, `/content/new`, Operations views | nothing                       | nothing                                                                                                                                                                                        | 0, the data is in memory                                                                                                                                                              |
| record, mouse or pen                                         | `loadHomeEditor()`: code only | `loadHomeEditor()` plus `startRecordRead(identity)` on `pointerdown` **where `event.button === 0` and no modifier key is held**, cancelled on the first `pointermove` past a 10 px slop radius | one script per session (408 KB gz today, about 235 KB gz after the CodeMirror deferral). one private read per qualifying press                                                        |
| record, touch or keyboard                                    | `loadHomeEditor()` on focus   | the read starts at **click**, never on `pointerdown`                                                                                                                                           | a scroll gesture beginning on a row fires `pointerdown` then `pointercancel`, which would spend 3 Durable Object RPCs plus 8 GitHub requests per scroll in production (proven counts) |
| Life, newsletter review, cross-workspace                     | nothing                       | nothing                                                                                                                                                                                        | documents, and `private, no-store` documents are not prefetched                                                                                                                       |

the button and modifier filter is not cosmetic. 2.3 filters non-primary buttons and modifiers at **click** time; without the same filter at `pointerdown`, a right-click to copy a row's link spends a private record read, whose measured cost is 3 Durable Object RPCs plus 8 GitHub requests (3.5). the slop cancel covers desktop drag-select, which begins with a qualifying primary `pointerdown` on a row and would otherwise start a read that only `pointerup` elsewhere cancels.

`record-read.ts` keeps one slot. an unclaimed read is aborted and its body cancelled on `pointercancel`, on the slop-radius `pointermove`, on a `pointerdown` elsewhere, or 1,500 ms after `pointerup` without a commit. a settled private record body never sits in memory for an abandoned press longer than that window. the click claims the in-flight promise, so a record never reads twice for one intent. the head start is the real `pointerdown` to `click` gap, which the current harness cannot credit because it fires hover, pointerdown and click within 1 ms (phase 1); S1 adds a real 80 ms press gap.

### 2.9 documents that remain

`middleware.ts` answers a request carrying a `Sec-Purpose` header outside the allowlist with an empty non-2xx (S8). this design creates no speculations, so the guard exists to foreclose a browser heuristic or a future change issuing a speculative request against a private document. a `speculative` count joins `SERVER_TIMING_METRICS` (`lib/server-timing.ts:14-24`) on owner responses only.

`page-lifecycle.ts` adds a `pageshow` handler. it has **two independent rules**, which an earlier draft collapsed into one and broke both.

**rule 1, signed out: check a marker sign out does not delete.** the earlier rule compared `sessionStorage["admin:editorial:saved-at"]` against the render time, but 3.1 and 3.4 clear that key on sign out, so after a sign out the key is absent, the comparison is false, no reload happens, and the restored document repaints every private inventory row to whoever presses Back. the mechanism must therefore key off something sign out **sets**, not something it removes. on `pageshow` with `persisted` true, read `localStorage[recoveryLogoutGenerationKey]` (`draft-recovery.ts:12`, raised by `clearEditorialRecovery` at `:88-96`, verified, source) plus a same-tab signed-out flag written by `Logout.tsx` before it navigates. if the generation differs from the value captured when this document hydrated, or the flag is present, `location.replace("/auth")` unconditionally. the only comparison is against a value sign out **writes**; there is no staleness arithmetic. residual, stated: when storage is denied, `Logout.tsx:68-71` skips the write and only dispatches the event, so neither marker exists and a bfcached page can still come back; S18 records that case as a known gap rather than a pass.

**rule 2, stale rows: compare per record, not per session.** a session-wide "anything was saved" flag reloads pages that are already correct, because bfcache restores JS state and a library whose rows were patched in memory by `dispatchEditorialRecordSaved` (`HomeEditor.tsx:510-532`, applied at `EditorialApp.tsx:146-155`) comes back right. the full reload then costs 54 requests and destroys the `#astryx-app-shell-main` scroll and focus that S18 also promises to restore, so the earlier rule could not satisfy its own acceptance. instead `admin:editorial:saved-at` becomes `admin:editorial:saved`, a map of saved record href to revision (hrefs and integers, no titles and no content, matching the 3.1 constraint). on `pageshow` with `persisted` true, compare each stored revision against the restored island's `revisions[href]` (the map `applyEditorialRecordSaved` already maintains and guards on, `editorial-inventory-events.ts:128-133`). every stored revision at or below the in-memory one: the page is already correct, no reload. any stored revision above it: the save happened in a **later document of the same tab** (for example a deep-linked record document), the restored page never saw the event, and the map carries no title to patch with, so reload once. `sessionStorage` is per tab, so this rule never sees another tab's saves; that staleness is stated in 3.3 and not claimed here.

the record-versus-library asymmetry the earlier draft relied on is **withdrawn**. it claimed "record pages fetch `no-store` responses so Chrome will not restore them; library pages will be", but bfcache eligibility keys off the main document response, and `middleware.ts:98`, `:110` and `:133` set `Cache-Control: private, no-store` identically on library and record documents (verified, source). there is no header-level difference to lean on, and the design does not claim one. S18 proves both rules under `--browser-defaults` on **both** a library URL and a record URL. `Clear-Site-Data: "cache", "prefetchCache", "prerenderCache"` (3.4) is a speculation guard and is not credited with bfcache eviction. R18 stays open until the S18 run exists.

### 3.2 props shape

`EditorialLayout.astro` already runs the inventory on every editorial document (`:50-54`). it serializes slim records once plus newsletter rows on `/content`, `/newsletter`, `/content/new` and record documents, and drops `searchEntries` (15.0 KB attr) and the subset groups (11.9 KB plain), which the client derives. record documents get rows for 15.0 KB attr, less than the 16.1 KB of `searchEntries` they carry today (proven sizes), which is what makes deep-link close in-island instead of a 53 to 55 request document (verified, spike s5).

**the field list comes from the draft, not from a server projection.** an earlier draft put a server-side `fieldShape` on record **documents** only, derived from `editorialInventory()` at `pages/content/[collection]/[id].astro:19-26`, and called it "what lets a record skeleton match a work record". it does not, for two reasons, both verified.

first, the in-island open (row 6) starts from the **library** document, whose props are slim rows. slim rows do not carry `fieldShape`, and carrying it for 149 records is budgeted nowhere, so on exactly the path S16 creates the placeholder would have no shape at all.

second, even on the deep-link path the two sides read different revisions. `editorialFields(record, data)` pushes one field per story section, one per story paragraph, one per technical heading and one per technical body, all off `data` (verified, source `lib/editorial-fields.ts:36-70`). the server projection reads the **published** entry; HomeEditor renders the **draft**, calling `editorialFields(record)` with no data while loading (`HomeEditor.tsx:735`) and `editorialFields(record, parsed.data)` once the draft parses (`:753`, both verified, source). a draft that adds one technical section or one paragraph diverges by two or one label-plus-control pairs, far more than 1 px.

so the rule is: **derive the placeholder field list from the same source the editor will use.** `record-read.ts` resolves the draft source first; `RecordRoute` runs `parseEditorialSource` and `editorialFields(record, parsed.data)` before rendering `EditorPlaceholder`. until that resolves there is no field list, so `EditorPlaceholder` renders the fixed chrome (h1, toolbar, tabs) plus **one** content-region box carrying `data-parity-content`, which the 4.3 content contract already allows to grow at its block-end edge. work records therefore never claim a per-field 1:1 match they cannot make; writing and page records, whose field lists never read `data` (`editorial-fields.ts:12-21` for writing, `:74-133` for pages, verified, source), keep the full per-field match.

record documents still pass a slim `fieldShape` (labels and rich flags, never values) as a first-paint hint for the deep-link case, but it is advisory: when it disagrees with the parsed draft, the parsed draft wins and the placeholder was the single content region, so nothing shifts.

guard rail: above 256 KB attr the layout omits rows on non-library documents, and `content-library` declines whenever rows are **absent**, for any reason including a reverted S13, so the switch degrades to a document rather than an empty library (estimate for the size bound; the absence check is a design rule tested in S13).

**a created record needs its own event.** today `NewWriting.tsx:190` does `window.location.assign("/content/writing/<slug>")`, a document load that re-runs the inventory, and that is the only thing that puts a new record in the library. rows 4 and 5 remove it: `/content/new` stays in the island and the create navigates through `router.navigate`, so the session never reloads. the existing patch path cannot insert. `applyEditorialRecordSaved` collects matches by href (`editorial-inventory-events.ts:118-124`) and returns `current` unchanged when `!matched.size` (`:126`, `:131`), then only maps over existing `groups[].records` and `searchEntries` (`:154-174`, all verified, source). without the new event the sequence `/content/new`, create "foo", edit, close to library leaves "foo" absent from Writing, from the group count and from palette search for the whole session. the event is scheduled in S4 beside the restore and publication-live dispatches, and S16 asserts "create then close shows the new row".

**"as today" was wrong for the other-tab row.** today every in-workspace switch is a document load, so rows refresh constantly; a stale row survives seconds. under this design a session can hold pre-edit rows from another tab indefinitely. the honest statement is: cross-tab staleness now lasts until a document load, and in-island sessions have very few of those. the mitigations are the in-tab events above plus `pageshow` rule 2 (2.9), which is per tab; nothing reconciles a second live tab, and this design does not add an inventory endpoint to do it.

with restore, publication-live, discard and create dispatching, the gap design (a) accepted (one document load per session after a publish or discard) closes for the **acting tab** without any inventory endpoint. it does not close for a second tab.

### 3.4 logout, expiry and back

| path                            | what clears                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**the one rule, written once: an open record's unsaved text is never destroyed by a session event.** an earlier draft had both rows above dropping the record snapshot, which destroys text that is currently recoverable. the cross-tab case is the sharp one: tab A signs out, `clearEditorialRecovery` raises the generation and sweeps every recovery key from the shared origin storage (`draft-recovery.ts:88-96`, verified, source), and tab B's dirty buffer newer than the recovery debounce then exists **only** in tab B's React state. today `localLogout` (`HomeEditor.tsx:693-706`, registered at `:707-708`) deliberately clears only the channel, the storage key and the saved-draft comparison, leaving `state` and `snapshot` alone precisely so the author can still read, copy and download the text. dropping the snapshot deletes the last copy. the expiry case is the same shape with a different trigger: an autosave `post` (`HomeEditor.tsx:478`, `:508`) maps 401 and 403 to "session expired" at `:471-473` (verified, source) and can fire while the author is typing.

so both paths do exactly this, and nothing more:

1. drop inventory rows, the palette entries derived from them, and the prefetch slot.
2. freeze the open editor read-only behind the signed-out or expired banner, keeping `state` and `snapshot`.
3. keep the `download()` action live: it serializes `editor.current.state.source` from memory (`HomeEditor.tsx:784-794`, verified, source), so it works after the sweep. `downloadBrowserRecovery` (`:49`, `:1256`) reads the swept envelope and is not relied on here. the banner copy matches section 5's refused-save row: "Download a copy before leaving this draft".
4. the snapshot goes only on an explicit author action, download or dismiss, or when the tab navigates.

section 5's Operations row is aligned to the same rule in the other direction: last-known machine rows are private observations too, so on `session_expired` they are dropped like inventory rows, and only the banner remains. `ObservabilityWorkspace.tsx:246-251` keeps its "Last known" labels for `disconnected` only, which is a transport failure inside a live session, not a lost session (verified, source: the label is gated on `status === "disconnected"`). ### 4.3 how parity is structural

1. the loaded component renders the frame. geometry comes from one component tree, not two drawings of it.
2. the frame, not the caller, emits `data-parity="<slot>"` on every slot. both states emit the same key set by construction, and the test fails on any missing or extra key.
3. small leaves the frame needs in both states move into the eager bundle: `DocumentTitle` (67 lines) and `SaveStatus` (103 lines). gz cost measured in the PR; above 5 KB gz they fall back to placeholders.
4. **the content contract:** a box carrying `data-parity-content` may grow only at its block-end edge and must be the last box in its column. every other box asserts x, y, width and height within 1 px. this turns "data-dependent heights cannot match" from a caveat into an assertion the geometry test enforces.
5. source-scan tests: `Skeleton` importable only under `loading/`, `AdminSkeleton` must not exist, `Spinner` not imported outside Astryx Button internals, `router.intent` called only from `AdminLink.tsx`, `record-read.ts` and `editor-chunk.ts` imported only by `RecordRoute.tsx`, `HomeEditor.tsx` and the record resolver. they follow the existing pattern of `scripts/ci/admin-fixture-boundary.test.mjs` and land with the loading PR, not at the end.

### 4.4 tables without a loading prop

Astryx `Table` takes `emptyState?: ReactNode | false` and no loading prop (verified, source `Table/types.ts:639`). `TableFrame` passes placeholder data through the real table:

```ts
type AdminColumn<T> = TableColumn<T> & { placeholder: () => React.ReactNode };
// loading: data = placeholderRows(n) -> [{ __placeholder: true, id: "placeholder-0" }, ...]
// each renderCell becomes: item.__placeholder ? column.placeholder() : column.renderCell(item)
```

header cells, `proportional` and `pixel` widths, density and `dividers="none"` are identical because the column array is identical. `n` is the page size capped to the rows that fit the viewport. empty results use `emptyState` so the header stays, which fixes the shift at `ContentLibrary.tsx:638-663`, `ObservabilityWorkspace.tsx:572-591` and `LifeWorkspace.tsx:376-388`.

### 4.5 exactly one announcement per wait

counting `[role=status]` nodes is wrong: every Astryx Button renders a hidden one (verified, source `Button/Button.tsx:730-733`) and owner builds add one (`EditorialWorkspaceShell.tsx:481-494`). counting raw text mutations is also wrong: `announceMessage` sets `textContent = ''` and re-sets it inside a `requestAnimationFrame` (verified, source `useAnnounce.ts:132-141`), so one announcement is two mutations.

the rule is therefore: **count announcements**, defined as a non-empty text set on an Astryx live region, observed with a MutationObserver that coalesces a clear plus re-set within one frame. only `useWaitAnnouncement` may announce during a navigation wait, placeholders are `aria-hidden` (`Skeleton.tsx:202`), and the waiting region carries `aria-busy`. the record open speaks once ("Opening <title>"), replacing today's two mounts (`EditorialApp.tsx:268-275` then `HomeEditor.tsx:735`).

**one wait owner for the record open: `RecordRoute`.** an earlier draft named the two mounts but never said which stops announcing, and S16's file list omitted `HomeEditor.tsx`. HomeEditor fetches its own record (`HomeEditor.tsx:493`) and renders its own loading return while that is pending (`:728-736`, today an `AdminSkeleton`, which is `role=status` with sr-only text, `AdminFeedback.tsx:18-24`, all verified, source). after S10 that inner return becomes a wait, so in S16 `RecordRoute` would say "Opening <title>", the module resolves, HomeEditor mounts with `!state && !snapshot`, and speaks again for the same open. the fix:

1. `RecordRoute` claims the record-read promise from `record-read.ts` and passes the resolved snapshot into HomeEditor as a prop (`initialRecord`).
2. HomeEditor skips its own read when `initialRecord` is present, so its loading return is unreachable on the in-island path. it keeps the read for the deep-link document path until S16 moves that path through `RecordRoute` too.
3. as a belt, both components use the same `waitId` (the record href), and `useWaitAnnouncement` dedupes across instances (4.2).

`HomeEditor.tsx` joins S16's file list, and S16 asserts the announcement count on a **cold** module open as well as a warm one, which R17 otherwise leaves unmeasured. the prototype already recorded `liveRegionMutations: 1` per in-island switch (proven, `routers-v3.json`). the harness and the parity test both assert exactly 1 across **both** AdminLayout roots, and additionally assert exactly **one** Astryx polite live region in the document on Operations and Life (R4).

**the metric changes in S1, so "today" numbers must be restated.** the committed harness counts `maxAnnouncements` as "the distinct role=status ancestors announcing them" (`scripts/admin/perf-measure.mjs:91`, computed at `:452-456`, verified, source), and the baseline's "status regions 2 / 2" for Library to record comes from that definition. this section declares that definition wrong. an acceptance written as "2 to 1" would compare two different metrics, and a green result could be a metric change rather than a behaviour change. so S1 emits **both** counts on the same runs for `load:record` and `switch:record`, publishes the restated "today" value under the new definition, and S10 and S16 cite only the restated number.

### 4.6 reduced motion and dividers

reduced motion: `Skeleton` sets `animationName: 'none'` under `prefers-reduced-motion: reduce` (verified, source `Skeleton/Skeleton.tsx:77-79`), the pulse only starts after `DELAY_TIME = 1000` (`:30`, `:112`), and `admin-interactions.css:24-31` sets `animation: none` on themed descendants. no transition is added to the swap.

dividers: placeholders are fills with no border. frames keep `dividers="none"` tables and no `hasDivider` layouts. the parity test asserts zero border widths on `[data-placeholder]` and no `hr` or `role=separator` inside a frame.

## result
