## Cross-route findings and decisions

1. **Inbox destination mismatch, corrected locally.** `data/admin.ts` defines Inbox as `/`; `AdminHome.astro` filters use `/` plus query; `life/index.astro` attention links use `/?item=...`. Root redirects these to Website Content. Change only Operations destinations to `/inbox` while preserving query. Keep the Website root redirect exactly as designed. The existing route parity test did not cover link consumers.
2. **Separate chrome and source ownership.** The new Website shell has an Operations link to `/inbox`. Operations still uses `AdminLayout`/`AdminShell` and its current authorized command sources. Its legacy Content group still mixes Git routes with old D1 review/draft/preview/history routes and Carousels; relabel as legacy diagnostics or organize under Operations without redirecting between record models. Handoffs remains under System rather than planned Work; Personal still labelled Life. No route deletion or data merger is appropriate.
3. **Source failure presentation.** Life, Health and Locations ignore availability fields; successful-empty and failed-read states need separate UI branches with existing retry/status destinations. Fleet should distinguish deliberately disabled production runtime, load error and genuinely empty observations. This requires presentation work over existing contracts, not new access. Proof needs clear static/durable provenance; its loader already returns some explicit failure records, so do not erase those into a generic error.
4. **Refresh and focus.** Inbox keeps stale DOM on polling failure but gives no persistent failure status. A changed poll reloads the whole page. Prefer quiet stale status and controlled update/focus preservation after a separate behavioral review; do not silently change data polling in this audit.
5. **Shared components and casing.** Operational shell uses Astryx AppShell/SideNav; Work uses Banner/EmptyState/Table, and Knowledge uses Banner/Button. Remaining native tables, custom cards, details and date rendering are not consistent with the proposed shared feedback/metadata patterns. SSR-only pages do not benefit from a decorative client skeleton added after data already arrived; introduce skeletons only at actual loading boundaries. Lowercase static/multiline labels remain in Work tabs, Knowledge filters, Auth, Locations, Gates and several diagnostic captions. Preserve provider names, authored titles and enum values while fixing interface presentation.
6. **Accessibility and mobile evidence still required.** Desktop/mobile shell controls, native details, inspector focus and the wide repository/deploy matrices require actual 1440/834/390/320 viewport and keyboard QA. Source labels and existing tests alone do not prove target sizes, responsive overflow, focus restoration or color contrast.
